§1Product Definition & Positioning

1.1 What it is

Priva Cloud is a self-hostable, Kubernetes-native, multi-tenant Agent Runtime built on the Claude Agent SDK. It gives each user an isolated, scale-to-zero agent-runner pod that runs full Claude Agent SDK sessions — skills, MCP servers, hooks, subagents, a web terminal, and a rich web console — while a stateless control plane handles identity, routing, pod lifecycle, and durable state.

The product occupies a deliberate intersection that (as §9 shows) no existing product covers: full Claude Code capability × per-user compute isolation × fully on-prem × bring-your-own-key. It is an internal platform product: the customer is the organization; the users are its employees and the platform team that governs them.

1.2 Users & personas

End user — internal employee

Gets a personal AI assistant with a real, persistent workspace: chat console with streaming and canvas, session history with fork/rewind, a PTY web terminal, a file explorer, personal skills / MCP servers / subagents / hooks. Brings their own model credentials (ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN).

Platform admin — operator of the fleet

Provisions and governs users via the admin SPA: user CRUD and self-registration approval, per-tenant resource specs and storage quotas, runner defaults, a hook policy (admin-stored hooks delivered through data-spine, force-on or user-optional), risky-tool policy, fleet snapshot, resource usage, system-health graph, gateway metrics, and an audited console into control-plane pods. PII masking is a separate programmatic post-tool filter driven by the sensitive-patterns knob, not a catalog hook.

Platform engineer — extends the runtime

Integrates internal systems by authoring MCP servers, skills, and plugins; consumes the runtime API (/api/sandbox/*, SSE / WebSocket) to embed agent sessions into other internal tools.

1.3 Primary use cases

  • Personal AI assistant with a real workspace — long-lived, resumable agent sessions that read and write files, run commands, and persist state per user, not per browser tab.
  • Agent access to internal systems — admin-governed MCP servers and skills expose internal APIs, databases, and tools to each user's agent under per-user credentials and hook-enforced policy.
  • Coding and operations work — the full Claude Code loop (terminal, file edits, git) inside the user's own isolated pod, driven from the browser.
  • Governed fleet operation — one platform team runs hundreds of agents with per-tenant quotas, audit trails, and centrally enforced guardrails.

1.4 Non-goals

Explicit non-goals keep the competitive argument (§9) honest and the architecture small:

  • Not a public SaaS. Designed for semi-trusted internal populations on shared cluster infrastructure — not for anonymous, adversarial tenants.
  • Not a model gateway or metering proxy. BYOK is a design decision: there are no virtual keys and no central token-billing path; usage is pod-self-reported. Routing via Bedrock / Vertex / internal proxies is the user's choice of base URL.
  • Not a re-implementation of the agent loop. The runtime wraps and spawns the real claude CLI via the Claude Agent SDK. Priva never forks the loop; it inherits upstream capability.
  • Not a no-code workflow builder. Extensibility is code-shaped (skills, MCP, hooks), not DAG-shaped. Workflow products (Dify, n8n) are complements, not targets.
  • Not chat-only. A chat UI without an isolated execution workspace is explicitly the thing Priva exists to surpass.

The web console follows a locked design system (web/design-spec.md) — metaphor: a living, hardcover technical manual — serious, precise, in control.

3.1 Request byte path

Every runtime request is steered per-request: the edge consults the control-panel EPP over Envoy ext_proc before forwarding to the tenant's pod. The edge terminates client transport and relays bytes; authoritative authentication and account resolution happen at the EPP. agentgateway is never on the byte path's far side — it relays; the EPP only decides.

3.3 The AgentTenant CR — one object per user

A tenant's entire runtime existence is declared by one namespaced custom resource (priva.io/v1alpha1, short name at). Provisioning a user = creating a CR; waking a pod = patching one field; offboarding = flipping desiredState.

apiVersion: priva.io/v1alpha1
kind: AgentTenant                  # one per account; CR name == accountId
spec:
  accountId: u-alice               # required
  username: alice
  desiredState: active             # active | offboarding | purge
  image: priva/agent-runner:dev
  agentRunnerType: auto_scale      # auto_scale | persistent (sweep-exempt)
  resources: { cpu: 1.0, memoryMb: 2048 }   # requests == limits → Guaranteed QoS
  storageGb: 1                     # hard quota; grow-only online expand
  idle: { graceSeconds: 1800, minAliveAfterWakeSeconds: 120 }
  concurrency: { maxConcurrentSessions: 3 }
  wake: { requestedAt: "…" }       # the ONLY scale-up trigger (EPP patches it)
status: { phase: Ready, podIP: … } # derived, never authoritative

4.3 Deferred hardening (Phase 6)

The alpha runs plaintext in-cluster (except the one TLS ext_proc hop) and shares a namespace between control plane and tenants. The following are designed but not yet in place: NetworkPolicies (default-deny + narrow egress) · mTLS / JWKS pod trust (alpha uses an HS256 signed header) · per-account KMS/DEK envelope encryption · edge TLS termination · Redis-based wake/idle coordination · a separate audit PVC, and moving control-panel's per-pod local audit into data-spine before scaling replicas (otherwise replicas fork audit history).

4.4 Open, high-risk: the web terminal

Launch blocker — review 2026-07-07, unremediated

The tenant-facing PTY is a live cross-tenant compromise chain. A shell (bash -l) inherits os.environ, which via envFrom contains the shared priva-shared-secret — the JWT and HMAC signing secrets, identical in every tenant pod. A single tenant can therefore forge a valid runner token for any account or admin. And with no NetworkPolicy, that shell can already reach every other ar-* pod, data-spine, redis, and control-panel directly by TCP — so the forged token opens a shell in another tenant's pod, whose only guard checks the token's account_id against the target pod. The BYOK model rests on two assumptions — "the pod is unreachable except via the edge" and "the signing secret is secret" — both currently false.

Tier-0 remediation (~1 day, not yet applied): env allowlist via execvpe (~10 lines) · default-deny NetworkPolicy + narrow egress · automountServiceAccountToken: false. Full write-up: docs/webterminal-blind-spot.md.

4.5 Egress & data-exfiltration control

§4.1–4.4 answer "can tenant A reach tenant B?" They do not answer "can data leave the platform?" — which, for a product sold on sovereignty, is the load-bearing question. Two authorized channels move data out regardless of any pod-to-pod policy:

ChannelThe exposureSafeguard (not built)
Model endpoint (BYOK)ANTHROPIC_BASE_URL can point at any host. Every turn ships the agent's context — files it read, tool outputs, secrets in scope — to that endpoint. A wrong or hostile base URL is a fully-authorized exfiltration pipe that no pod NetworkPolicy inspects.An admin endpoint allowlist (only approved model gateways / internal proxies), enforced at the pod's egress and validated when BYOK credentials are saved. Block direct-to-internet model calls unless whitelisted.
Agent tool egressAn autonomous agent that browses the web or calls APIs can POST data outward, or SSRF into internal services it was never meant to reach.Default-deny egress NetworkPolicy + a per-tenant allowlist of reachable hosts; a mandatory egress proxy with DLP inspection as the only outbound path; the PII-masking hook extended to outbound payloads, not just tool inputs.
Why this outranks the tenant-isolation work

On-prem keeps data off the vendor's cloud; it does not, by itself, stop the agent from mailing the data out. This is the same class of risk as the web-terminal finding but wider — it applies to every agent, not only terminal users, and it directly contradicts the sovereignty guarantee that is Priva's headline differentiator (§9). Recommendation: route both channels through one chokepoint — a mandatory egress proxy that also enforces the model-endpoint allowlist — so exfiltration has a single control point and a single audit log. Pairs with brokered credentials (§11.4) and the inbound-trust profile (§11.5).

7.3 Auditing

Auditing runs on two planes, both via priva_common.audit_log — daily-partitioned JSON-Lines with cursor pagination:

  • Per-account (data plane) — written by agent-runner to the per-account audit volume /audit/<account_id>: tool and skill invocations, run completions, session operations, and permission decisions. Surfaced to the user through the Data & Usage view (/user/{overview,stats,audit,analytics} — a 183-day usage heatmap, audit log, and analytics timeline).
  • Control plane — written by control-panel for admin actions: user CRUD, registration approvals, config changes, and the audited K8s-exec console (WS /api/admin/console/ws). Retention is governed by the admin history-retention knob.
Known gap

7.4 Distributed tracing

Current state — not yet implemented

There is no end-to-end distributed tracing today. A single runtime request already crosses four hops — edge → EPP (ext_proc) → operator (CR patch) → agent-runner → model gateway — and correlating them currently means stitching per-service logs and audit rows by hand.

The hard segment is structural: the wake path is asynchronous and eventually-consistent — the EPP patches the AgentTenant CR and the operator reconciles it into a running pod; there is no synchronous call to hang a child span on. A real tracing story would need W3C traceparent propagation injected at the edge, carried across the ext_proc metadata into the EPP and onward into the runner and the SDK turn, with the CR carrying a correlation id so the operator's reconcile can emit a linked span, all exported to an OpenTelemetry collector. This is a forward item, not a config flip.

7.5 Logging

Services log through a shared loguru-based logger (get_app_logger) to stdout for cluster-level aggregation. Because it is loguru, messages use brace {} placeholders — a printf-style %s prints literally — a small but real footgun captured in the platform's own notes. Structured fields (account, session, run id) travel in the log record so downstream aggregation can pivot on them; the same identifiers key the audit rows in §7.3.

7.7 Fairness, wake-stampede & warm pools

Current state (honest). Every wake is a cold start (≈4 s); there is no warm pool. Because idle tenants sit at 0 replicas, a synchronized burst — a 9am login wave, or a scheduled-job fan-out — is N simultaneous cold starts hitting the scheduler, image cache, and node capacity at once. The designed global wake-concurrency limiter (~20 in-flight) bounds the stampede but converts it into a queue; per-account concurrency caps (default 3 sessions) bound a single noisy tenant. There is no cluster-level fair-share across accounts today.

Setting up a warm pool (proposed)

The binding constraint (tier 2)

Kubernetes cannot hot-attach the per-account subPath volume to an already-running pod, so a claimed warm pod resolves one of two ways: (a) app-scoped bind — the warm pod mounts the shared RWX priva-export root and the runtime scopes to /<account_id> on claim (fastest, no restart, but isolation becomes app-enforced until the pod is recycled — acceptable only with the §4.5 egress controls and a hard recycle-after-session policy); or (b) warm-then-recreate — the warm pod proves node + image + process readiness, then a fast Recreate attaches the real per-account volume (preserves the kernel-mount boundary, still far quicker than cold because node and image are hot). Sizing: pool ≈ expected concurrent cold starts at P95 peak; a fair-share wake queue (round-robin across accounts, not FIFO) stops one account's fan-out from starving others.

Upstream path

The CRD already models states: active → offboarding (pod scaled to 0, data retained, access revoked) → purge (data destroyed). Erasure and backup are one problem

A defensible right-to-erasure must destroy every copy — the workspace subPath, the audit volume, the data-spine rows, the API-key ciphertext, and any backups/snapshots — then emit a tamper-evident purge record (the one artifact kept). You cannot prove erasure without an inventory of every backup that holds a copy, which is why the two are inseparable.

Backup & DR (currently absent — recommendation)

  • data-spine: a single SQLite file → scheduled online backup (WAL copy) to off-node storage, with a documented RPO (e.g. ≤ 24 h) / RTO; the Postgres HA path (stub today) is the real fix.
  • Workspaces: per-account CSI VolumeSnapshot on the prod CephFS/NFS backend on a schedule. The session JSONL is the record and has no other redundancy today — a lost volume is lost agent memory.
  • Restore drills: an untested backup is not a backup — rehearse restore periodically, alongside the offboard→purge chaos tests (Phase 6).
Honest status

The CRD lifecycle states exist; the retention window, legal hold, export, erasure-proof, and the entire backup/DR layer are recommendations, not code. Set RPO/RTO targets before any HA or compliance claim. Tracked in §12.

8.6 Upgrade & rollout lifecycle

How the fleet moves forward when the agent-runner image, the baked-in claude CLI, or the SDK changes — the operational counterpart to the "SDK churn" risk (§12).

  • Control plane: stateless services roll normally. Two catches: control-panel binds the in-process EPP on :9000, so scale/roll by replica count, never uvicorn --workers; and its per-pod local audit must move to data-spine (§7.3) before running >1 replica, or a rolling upgrade forks audit history.
  • Tenant pods: the CRD carries a per-tenant image, so the fleet can hold deliberate version skew — but nothing governs rollout today. Recommended: a canary cohort (a few accounts pinned to the new image) gated on an eval pass, then staged promotion of the default image. Parked pods pick up the new image on their next wake — scale-to-zero doubles as a free rolling upgrade for idle users, with zero coordinated downtime. Running pods drain-and-recreate at session end or on admin-forced restart.
  • Session compatibility: session healing (orphan tool-use repair on resume) absorbs minor drift; a breaking claude/SDK change needs a session-format compatibility check and, worst case, a read-only fallback for old transcripts (ties to the deferred state-reader, §5). Pin the CLI version per image so skew is explicit.
  • Rollback: because wake pulls the current default image, rollback = repoint the default and force-restart; parked pods self-heal on next wake.
Scale-to-zero makes upgrades cheap

Most pods are off, so most users upgrade on next login with no coordinated downtime — an underappreciated benefit of the tenancy model. The real work is the canary/eval gate and the session-format compatibility check, not the mechanics.

§11Design Evolution & Extension Paths

The current architecture was built for one user driving one agent from a browser. The capabilities below stretch that to agents driving agents, humans approving out-of-band, and agents shared across users. For each, the design already supplies most of the substrate; the value is in seeing exactly where it holds and where it must change. These are design directions, not committed roadmap (§10).

The through-line

Pod-per-tenant + EPP steering + permission/hook governance turns out to be a strong substrate for all four expansions: a published configuration is instantiated in the caller tenant, while only a service-style shared running instance becomes its own tenant; an A2A call is just a wake, an out-of-band approval is just a durable permission_request, and brokered MCP auth is just control-panel doing for tools what it already does for runner tokens. What each demands in return is mostly the hardening already on the Phase 6 list (NetworkPolicy, mTLS/JWKS, KMS/DEK) plus durability for the permission coordinator. The expansions don't fight the architecture — they cash in its deferred security cheques.

11.1 Agent-to-agent (A2A) interoperability

Current substrate. agent-runner already consumes tools over MCP (agent→tool) and runs in-pod subagents; the agentgateway edge is an AI-native L7 proxy; and the EPP already provides per-agent identity, wake-on-demand, and per-request steering. The multi-agent workflow inspector already models and persists multi-agent runs.

Already prototyped — the remote-agentsandbox skill. A2A is not hypothetical here: a bundled skill (services/agent-runner/.../bundled/skills/remote-agentsandbox) already lets one Priva agent delegate a task to another over the standard runtime SSE contract. The mechanism is deliberately thin — which is the point: an agent calling another agent is just an agent acting as a normal client of the runtime API, no new protocol invented.

How it works today

The caller agent POSTs the ordinary AgentRunRequest body {message, session_id?} to POST /api/agent/run/stream (endpoint set by AGENT_SANDBOX_GATEWAY_URL) with Authorization: Bearer <token>, streams the SSE events, discards the intermediate assistant / tool_use / tool_result / task_* events, and keeps only the terminal result — whose payload already carries session_id, is_error, num_turns, duration_ms, total_cost_usd, and usage. Multi-turn continuity is a platform-minted session_id persisted in a local session.json (the immutable-session-id principle, §2). Concurrency is guarded by a non-blocking fcntl.flock on <session_id>.lock that fail-fasts (exit 4) — because the remote agent keeps on-disk conversation state that concurrent calls would corrupt. The bearer token lives only in the request header, never reaching the model.

HITL is present at the delegation seam: the skill instructs the caller to confirm destructive production operations with a human first.That confirmation is prompt-instructed, not platform-enforced → the approval inbox (§11.2); and there is no inbound authorization on the callee (who may drive it) → §11.1 safeguards below.

What full A2A adds. Each tenant agent becomes both a caller of and a callable endpoint for other platforms' agents (e.g. the emerging Agent2Agent protocol and agent cards). An external agent addresses "user X's agent"; the EPP wakes that pod exactly as it does for a browser request — the wake-on-demand + runner-token model maps onto A2A almost unchanged, and the gateway skill is the working proof of the caller half.

Future usage. The path from prototype to platform capability is legible: promote the AgentRunRequest/SSE contract into Priva's native A2A dialect and add an adapter that maps external Agent2Agent / agent-cards onto the same endpoint, so the edge + EPP front every tenant agent as an addressable, wake-on-demand A2A peer with the runner token as its capability. That unlocks an agent mesh — multi-hop A→B→C delegation, which the multi-agent workflow inspector already models in-pod — where published "production agents" are their own tenants (§11.3), reached through this exact gateway under brokered per-caller credentials (§11.4), enforced human approval (§11.2), and cost rolled up across the mesh from the total_cost_usd each hop already returns (§11.5).

Safeguards this demands

An inbound A2A call is an untrusted external party driving a privileged pod — the classic confused-deputy problem. It needs: agent-level ACLs (who may invoke whom), a constrained inbound permission profile (never bypassPermissions, an expanded disallowed-tool set, mandatory hooks), loop/recursion limits (A→B→A), rate limiting, and full audit of every cross-agent call. BYOK cost attribution also breaks — whose key pays when B drives A? (see §11.5).

11.2 Asynchronous HITL & the Feishu approval inbox

Current substrate. Synchronous, in-session human-in-the-loop already works: the permission coordinator emits a permission_request, parks an in-pod asyncio.Future, and resolves it on POST …/permission/respond. The deferred channel-connector (Phase 4) plus the channel_binding table (Feishu user ↔ account, already in the schema) supply the addressing.

What the inbox adds. When an agent hits an approval point while running detached — a scheduled job, an A2A-driven task, a long batch — with no browser open, route the request to the user's Feishu inbox; the human approves there; the agent resumes.

The architectural catch

The in-pod asyncio.Future is ephemeral. If the pod scales to zero while awaiting a human who takes hours, the pending decision is lost. Async HITL therefore forces the current scale-to-zero + in-memory-coordinator design to gain durability: (1) persist pending approvals (data-spine or PVC), not a Future; (2) exempt pods with open approvals from the idle sweep, or make the decision re-hydratable on wake; (3) sign approval links with short expiry so a Feishu message can't be forged into an approval; (4) a timeout/escalation policy that defaults to deny; (5) audit of the approver's identity. The permission model is the right seam — what changes is persistence and delivery, which is exactly the Phase 4 scheduler + channel-connector work.

11.3 Shareable / publishable agents & filesystem safeguards

Current substrate. A subagent + its skills + MCP servers + system prompt + hooks already constitute a reusable "agent definition," and the Skills hub is a working publish/consume pattern. Two sharing models follow, with very different risk:

  • (a) Publish the configuration — others instantiate the agent in their own isolated pod. Safe, and it fits the design today: isolation and BYOK stay per-instantiator.
  • (b) Share a running agent — others send tasks to your instance. Dangerous: their inputs now drive an agent inside a pod that holds your workspace, your BYOK, and your MCP credentials.
Binding decision · 2026-08-07

v1 selects model (a): A publishes an immutable Definition and B instantiates it in B's existing tenant pod; no per-Agent or per-run pod is added. “Safe” here means the A/B tenant boundary remains the pod boundary, not that a third-party Definition inherits all of B's pod-visible authority. An unreviewed Definition that can use Bash or file tools must use the public-restricted profile: an outer bubblewrap mounts only B-approved directories, shares the pod network, and is paired with tool-path enforcement and credential-environment scrubbing; trusted/owner-authored Definitions are not forced into it. See ADR-0004 for the threat model and acceptance gates. The “published agent as its own tenant” model below applies only to service-style model (b), not to v1 model (a).

The clean model

Treat a published agent as its own tenant — its own AgentTenant CR, its own pod, its own scoped volume and service credentials — invoked by others via A2A (§11.1) with per-caller auth and audit. This reuses scale-to-zero, pod isolation, and EPP steering wholesale: a publishable agent is simply a tenant whose "user" is a shared service identity.

Filesystem safeguards (model b, or any inbound-shared session)

An untrusted consumer could ask a shared agent to read the author's files and return them — data exfil by confused deputy. Required guards: a jailed / ephemeral scratch workspace seeded only with what the agent needs, never the author's ~/.claude/projects; read-only or per-invocation temp dirs; a locked-down permission profile + mandatory hooks; a default-deny egress NetworkPolicy so it can neither escalate tools nor exfiltrate; and credential decoupling — dedicated service creds or brokered MCP tokens (§11.4), never the author's personal BYOK. Sharing amplifies blast radius, which promotes the §4.4 web-terminal / NetworkPolicy hardening from "deferred" to "prerequisite."

11.4 Unified MCP / skill authentication

Current substrate. MCP config comes from .mcp.json + settings.json; the built-in FileCanvas server is in-process and needs no auth. External MCP server credentials, though, live per-pod today (settings / secret mount) — effectively per-user manual configuration.

What unification adds. When many users' agents reach the same internal MCP servers (issue trackers, databases, internal APIs), no user should hold raw service credentials. Following the emerging MCP OAuth 2.1 / resource-indicator direction, a central broker issues per-user, per-server scoped tokens, flows the user's identity through so the MCP server enforces per-user access, and centralizes rotation and revocation.

Design fit

control-panel is the natural broker — it already mints runner tokens and owns identity. It would register each MCP server with its auth method (OAuth client / API key / mTLS), broker short-lived per-user access tokens at wake or on demand, inject them scoped into the pod's MCP config, audit MCP tool calls under the acting user, and rotate without touching pods. Skills that shell out to external services get credentials the same brokered way instead of embedding secrets.

The tension to manage

This concentrates high-value secrets in the control plane — in tension with the "control plane never touches runtime data" principle. Resolve it by having the broker hold only long-lived refresh material and hand pods short-lived scoped access tokens, which reinforces the Phase 6 per-account KMS/DEK need rather than working against it.

§14Stakeholder Challenges — the hard questions

The same spec, read adversarially from each audience's seat. These are the questions a skeptic in each role would put to the team — deliberately aimed at the places the document itself already admits the honest answer is "not yet." A product earns the room not by having no gaps, but by naming them before the reviewer does.

14.1 The end user — "will this help me, and is my stuff safe?"

  • Why do I wait ~4 seconds every time my agent was idle? (§7.7 — warm pool designed, not built.)
  • If my pod's volume dies, is my session history and workspace just gone? What's backed up? (§8.5 — no backup today; the JSONL is the only copy.)
  • It's my API key paying — what stops a runaway agent from burning it overnight while I'm away? (§12 — no spend cap or circuit breaker.)
  • Who can actually read my files and transcripts — admins? other users? (Control plane never sees runtime data, §2 — but admin cross-file browse, §5, and the web-terminal exposure, §4.4, complicate the clean answer.)
  • Honestly, why not just use claude.ai or Claude Code on the web? (§9 — sovereignty + BYOK is the answer, but the console has to keep pace.)

14.2 The engineering leader — "why build, and why won't it be throwaway?"

  • Anthropic rents this exact runtime at $0.08/session-hour with the sandbox, vaults, and SDK churn handled. Justify the headcount to build and operate instead. (§9.3 — the case rests on sovereignty/BYOK/product, never on cost.)
  • You're welded to a fast-moving SDK/CLI. What happens the week a breaking change strands live sessions? (§8.6 upgrade lifecycle, §12 churn.)
  • Is this Manus-class autonomy, or a chat + terminal wrapper? Show me the path to "give it a goal, get a finished deliverable." (§9 honest-costs card, item 1 — real, ongoing agent-UX work.)
  • Agent Sandbox may commoditize the pod-runtime layer in 12–18 months. Why isn't half of this wasted? (§9 / §12 — keep the runtime layer swappable, differentiate up-stack in tenancy/console/BYOK.)
  • You claim "hundreds." What breaks at 2,000, and where's the multi-cluster / HA story? (kopf escape hatch >800 CRs; single-namespace alpha; data-spine SPOF, §7.8.)

14.3 The security lead (CISO) — "what's my blast radius?"

  • A tenant with a shell can read the shared signing secret and forge a token for any account or admin — and you shipped it unremediated. Why is anything else being discussed first? (§4.4 — open, launch-gating.)
  • BYOK to any base URL plus un-governed egress means the agent can mail our data anywhere. How is "sovereign" true? (§4.5 — the sharpest gap; egress control not built.)
  • Skills and MCP servers are unreviewed code in privileged pods. What stops a poisoned shared skill? (§12 supply chain; §11.3 — no signing/review/provenance yet.)
  • Shared-kernel isolation for semi-trusted users running arbitrary code with a PTY — where are gVisor/Kata, NetworkPolicy, mTLS? (§4.3 — all Phase 6.)
  • Prompt injection from a fetched page or file → exfiltration. What's the actual defense, not the aspiration? (§11.5 inbound-trust profile; the OpenClaw lesson, §9.)
  • You advertised "centrally enforced guardrails," but the admin→runner config channel was silently disconnected in K8s — the monolith wrote control-panel's own local .priva.settings.yml while runners read a per-account copy, so enforced_hook_ids never had a writer and enforced hooks never reached a single pod. What else is claimed-but-unwired? (Remediated for hooks: the hook policy now flows through data-spine hook_policy → runner snapshot at session-build, tamper-resistant outside the account mount. The other legacy knobs on that channel — preset-prompt, risky-tools, sensitive-patterns/PII, cli-path, history-retention — are still routed the old way and are the next migration, §5 config knobs.)

14.4 The SRE / operator — "what happens at 3am?"

  • data-spine is one SQLite writer with no backup — a pager with no runbook. RPO/RTO? Restore drill? (§7.8 failure matrix; §8.5 — unbuilt.)
  • No end-to-end tracing across a four-hop async wake path. How do I root-cause a slow or failed request? (§7.4 — not implemented; the async CR-wake is the hard segment.)
  • 9am is N simultaneous cold starts. What's the capacity model, and where's the warm pool? (§7.7 — three-tier design proposed, none built.)
  • control-panel audit is per-pod local, so I can't run it HA without forking history. Fix date? (§7.3 / §8.6.)
  • Rolling a new runner image to hundreds of parked pods — and rolling back — safely. Show me the procedure. (§8.6 — canary + eval gate; scale-to-zero helps, governance is the work.)

14.5 Compliance & finance — "can we defend this to an auditor and a budget?"

  • GDPR erasure: prove a departed employee's data — including every backup — is gone. (§8.5 — erasure and backup are one, unbuilt, problem.)
  • Where does data physically live, what's the retention window, is there a legal hold? (§8.5 — recommended, not built.)
  • Your competitors claim SOC 2. What's our control framework and audit-evidence story? (Audit trail exists, §7.3; a formal compliance posture is not yet a section — an open gap.)
  • BYOK means no central metering — how do we forecast, attribute, and cap spend across hundreds of users? (§7.6 pod-self-reported; §11.5 attribution; §12 cap — all unbuilt.)
  • Total cost of ownership versus just buying Claude Enterprise seats for the same headcount? (§9.3.)
The honest scorecard

Sorting every challenge above by what the team can actually say out loud today:

  • Answerable now — the tenant-isolation model, the sovereignty/BYOK rationale, the build-vs-adopt logic, and the shipped feature surface (§3–§6, §9). These survive the room.
  • Designed, not built — warm pools, backup/DR, tracing, unified auth, the HITL inbox (§7.7, §8.5, §7.4, §11.4, §11.2). Credible answers exist on paper; none has run in anger.
  • Open and gating — the web-terminal secret exposure (§4.4) and egress/BYOK exfiltration (§4.5). Until these close, the honest answer to the CISO is "not yet," and that is the answer that decides launch.

The test this section sets is simple: can the team give these answers without flinching? Where it can't, the spec has at least done its one non-negotiable job — naming the gap before the reviewer does.
