§1产品定义与定位

1.1 它是什么

Priva Cloud 是一个基于 Claude Agent SDK 构建的可自托管、Kubernetes 原生、多租户 Agent Runtime。它为每个用户提供一个隔离的、scale-to-zero 的 agent-runner pod，运行完整的 Claude Agent SDK 会话 —— skills、MCP 服务器、hooks、subagents、Web 终端以及功能丰富的 Web 控制台 —— 同时由一个无状态控制平面负责身份、路由、pod 生命周期与持久化状态。

本产品占据了一个刻意选择的交集，而（如 §9 所示）现有产品无一覆盖：完整 Claude Code 能力 × 每用户计算隔离 × 完全本地部署 × 自带密钥（BYOK）。它是一个内部平台产品：客户是组织本身；用户是组织的员工，以及治理他们的平台团队。

1.2 用户与角色

终端用户 —— 内部员工

获得一个拥有真实、持久工作区的个人 AI 助手：带流式与 canvas 的聊天控制台、支持 fork/rewind 的会话历史、PTY Web 终端、文件浏览器、以及个人 skills / MCP 服务器 / subagents / hooks。自带模型凭证（ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN）。

平台管理员 —— 集群的运维者

通过管理端 SPA 开通并治理用户：用户 CRUD 与自助注册审批、每租户资源规格与存储配额、runner 默认值、一套钩子策略（管理员存储、经 data-spine 下发的 hooks，可强制或由用户自选）、风险工具策略、集群快照、资源用量、系统健康图、gateway 指标，以及一个进入控制平面 pod 的受审计控制台。PII 脱敏是由「敏感模式」开关驱动的独立进程内后置过滤器，并非目录中的 hook。

平台工程师 —— 扩展运行时

通过编写 MCP 服务器、skills 与 plugins 集成内部系统；消费运行时 API（/api/sandbox/*、SSE / WebSocket）以将 agent 会话嵌入其他内部工具。

1.3 主要用例

  • 拥有真实工作区的个人 AI 助手 —— 长期存续、可恢复的 agent 会话，能读写文件、运行命令，并以用户为单位持久化状态，而非以浏览器标签页为单位。
  • Agent 访问内部系统 —— 由管理员治理的 MCP 服务器与 skills，在每用户凭证与 hook 强制策略下，将内部 API、数据库与工具暴露给每个用户的 agent。
  • 编码与运维工作 —— 在用户自己隔离的 pod 内运行完整的 Claude Code 循环（终端、文件编辑、git），从浏览器驱动。
  • 受治理的集群运营 —— 一个平台团队即可运行数百个 agent，带每租户配额、审计轨迹与集中强制的护栏。

1.4 非目标

明确的非目标让竞争论证（§9）保持诚实，也让架构保持精简：

  • 不是公有 SaaS。面向共享集群基础设施上的半可信内部人群设计 —— 不面向匿名、对抗性的租户。
  • 不是模型 gateway 或计量代理。BYOK 是一项设计决策：没有虚拟密钥，也没有中心化的 token 计费路径；用量由 pod 自行上报。经由 Bedrock / Vertex / 内部代理的路由，取决于用户对 base URL 的选择。
  • 不是对 agent 循环的重新实现。运行时通过 Claude Agent SDK 封装并拉起真实的 claude CLI。Priva 从不 fork 该循环；它继承上游能力。
  • 不是无代码工作流构建器。可扩展性是代码形态（skills、MCP、hooks），而非 DAG 形态。工作流产品（Dify、n8n）是补充，而非竞争目标。
  • 不是纯聊天。一个没有隔离执行工作区的聊天 UI，正是 Priva 存在的意义所在 —— 要去超越它。

§2设计原则

2.1 平台原则

原则陈述与后果
SDK 原生，绝不重新实现agent-runner 封装 claude-agent-sdk，后者拉起烘焙进镜像的真实 claude CLI。Skills、hooks、权限模式、subagents、fork/rewind 从上游免费获得 —— Priva 的工程预算投向租户与产品，而非追逐 agent 循环。
每租户一 pod 的隔离租户边界是一个 Kubernetes 对象（由 AgentTenant CR 调谐出的 Deployment / Service / PVC / Secret），而非应用层校验。每个运行时请求都终结在一个永远只属于某一用户的 pod 内。
Scale-to-zero 的经济性空闲租户的算力成本近乎为零：pod 保持 0 副本，直到 EPP 唤醒它们（≈4 s），随后 operator 在一段空闲宽限期后将其回收。数百个已开通用户 ≠ 数百个运行中的 pod。
控制平面绝不接触运行时数据会话、transcript 与文件仅存于租户 pod 及其每账号卷上。control-panel 只看到控制元数据（账号、配额、规格）—— 控制平面被攻破也读不到用户工作区。
单写者持久化状态所有持久化的控制平面状态都流经 data-spine：一个位于稳定 gRPC 契约（priva.dataplane.v1）之后的 SQLite WAL 写者。任何服务都不直接触碰数据库；存储引擎可替换（已有 Postgres stub）而不破坏契约。
唯一扩缩者 operator恰有一个组件（kopf operator）扩缩租户 pod，且仅由 AgentTenant CR 驱动。唤醒请求即 CR patch；不存在第二条可变更集群状态的路径。
权威鉴权位于 edge 的大脑每个运行时请求都逐请求转向：edge 经由 Envoy ext_proc 咨询 EPP，后者验证 JWT、解析出账号，并签发一枚绑定该账号的 runner token。Runner 只信任该签名，别无其他。
BYOK，无计量代理模型凭证归用户自有，且仅存于用户自己的 pod —— 由 pod 自身写入租户 PVC 上的 /workspace/.claude/settings.json，由 claude CLI 原生读取。平台从不终结、存储或计量模型流量；token 用量由 pod 自行上报。
文件系统即会话存储会话是租户卷上 ~/.claude/projects/ 下的 JSON-Lines —— 文件就是记录。中心数据库只保存账号与控制元数据，绝不保存 transcript 内容；claude CLI 原生读取的文件（.mcp.json、settings.json）以文件形式存在，没有会漂移的数据库镜像。
平台铸造的、不可变会话 ID每一处锁、路由与绑定都以平台铸造的稳定 session_uuid 为键，绝不用 CLI 派生的 id。唯一被许可铸造新 id 的路径是显式的 fork。
Strangler 迁移平台正被逐阶段地从一个可用的单机 monolith 中剥离出来；在 Phase 4 移除它之前，monolith 一直作为行为参照物。每个阶段都在 minikube 上端到端验证落地。

2.2 体验原则

Web 控制台遵循一套锁定的设计系统（web/design-spec.md）—— 隐喻：一本活的精装技术手册 —— 严肃、精确、尽在掌控。

  • GitHub-Dark 工业极简主义 —— Vercel × Linear 式的克制；无渐变、无玻璃拟态、无阴影；深度仅靠分层的背景色调呈现。
  • 状态是一条 2px 左边框 —— running/success/error/pending 均为边框颜色，绝不用圆点或填充背景；同一套语言延伸至实时 System Map 中带动画的字节路径连线。
  • 用骨架屏，不用转圈 —— 首次加载以真实内容的形状微光闪烁；状态流转为 skeleton → loaded，中间无过渡态。
  • 永不横向滚动 —— 每个容器都会断词，并在内部滚动过宽内容。
  • 危险操作需键入确认 —— 破坏性操作（删除历史、停止任务）要求键入确认文本，与平台服务端的风险工具强制策略相呼应。

3.3 AgentTenant CR —— 每用户一个对象

一个租户的整个运行时存在，由一个带命名空间的自定义资源声明（priva.io/v1alpha1，短名 at）。开通一个用户 = 创建一个 CR；唤醒一个 pod = 修改一个字段；下线 = 翻转 desiredState。

apiVersion: priva.io/v1alpha1
kind: AgentTenant                  # one per account; CR name == accountId
spec:
  accountId: u-alice               # required
  username: alice
  desiredState: active             # active | offboarding | purge
  image: priva/agent-runner:dev
  agentRunnerType: auto_scale      # auto_scale | persistent (sweep-exempt)
  resources: { cpu: 1.0, memoryMb: 2048 }   # requests == limits → Guaranteed QoS
  storageGb: 1                     # hard quota; grow-only online expand
  idle: { graceSeconds: 1800, minAliveAfterWakeSeconds: 120 }
  concurrency: { maxConcurrentSessions: 3 }
  wake: { requestedAt: "…" }       # the ONLY scale-up trigger (EPP patches it)
status: { phase: Ready, podIP: … } # derived, never authoritative

4.3 推迟的加固（Phase 6）

alpha 在集群内以明文运行（除那一跳 TLS ext_proc 外），且控制平面与租户共享同一命名空间。以下已设计但尚未落地：NetworkPolicies（默认拒绝 + 收窄出站）· mTLS / JWKS pod 信任（alpha 使用 HS256 签名头）· 每账号 KMS/DEK 信封加密 · edge TLS 终结 · 基于 Redis 的唤醒/空闲协调 · 一个独立的审计 PVC，以及在扩容副本之前把 control-panel 的每 pod 本地审计迁入 data-spine（否则副本会分叉审计历史）。

4.4 未决、高风险：Web 终端

上线阻断项 —— 2026-07-07 评审，未修复

面向租户的 PTY 是一条活的跨租户攻陷链。一个 shell（bash -l）会继承 os.environ，后者经由 envFrom 包含共享的 priva-shared-secret —— JWT 与 HMAC 签名密钥，在每个租户 pod 中完全相同。因此单个租户即可为任意账号或管理员伪造一枚有效的 runner token。而由于没有 NetworkPolicy，该 shell 已能通过 TCP 直接抵达其他每一个 ar-* pod、data-spine、redis 与 control-panel —— 于是伪造的 token 便能在另一个租户的 pod 中打开一个 shell，而该 pod 唯一的防护只是拿 token 的 account_id 去比对目标 pod。BYOK 模型建立在两个假设之上 ——「pod 除经 edge 外不可达」与「签名密钥是保密的」—— 二者当前均不成立。

Tier-0 修复（~1 天，尚未应用）：经由 execvpe 的环境变量白名单（~10 行）· 默认拒绝的 NetworkPolicy + 收窄出站 · automountServiceAccountToken: false。完整记述：docs/webterminal-blind-spot.md。

4.5 出站与数据外泄控制

§4.1–4.4 回答的是「租户 A 能否抵达租户 B？」它们并未回答「数据能否离开平台？」—— 而对一个以主权为卖点的产品，这才是承重的问题。有两条被授权的通道，无论任何 pod 间策略如何，都会把数据搬出去：

通道暴露面防护措施（未构建）
模型端点（BYOK）ANTHROPIC_BASE_URL 可指向任意主机。每一轮都会把 agent 的上下文 —— 它读过的文件、工具输出、作用域内的秘密 —— 送往该端点。一个错误或敌意的 base URL，就是一条完全被授权、且没有任何 pod NetworkPolicy 检查的外泄管道。一份管理员端点白名单（仅限已批准的模型 gateway / 内部代理），在 pod 出站处强制，并在保存 BYOK 凭证时校验。除非在白名单内，否则阻断直连互联网的模型调用。
Agent 工具出站一个能浏览网页或调用 API 的自主 agent，既可以把数据 POST 出去，也可以 SSRF 进入它本不该抵达的内部服务。默认拒绝的出站 NetworkPolicy + 每租户可达主机白名单；一个强制的、带 DLP 检查的出站代理作为唯一的出站路径；把 PII 脱敏 hook 扩展到出站载荷，而不仅限于工具输入。
为何这件事的优先级高于租户隔离工作

本地部署把数据挡在厂商云之外；但它本身并不能阻止 agent 把数据寄出去。这与 Web 终端发现属于同一类风险，但范围更广 —— 它适用于每一个 agent，而不仅是终端用户，并且它直接违背了作为 Priva 头号差异化卖点的主权保证（§9）。建议：把两条通道都收束到一个咽喉点 —— 一个同时强制模型端点白名单的强制出站代理 —— 使外泄只有单一控制点与单一审计日志。与经纪凭证（§11.4）及入站信任画像（§11.5）配套。

7.4 分布式追踪

当前状态 —— 尚未实现

当前没有端到端的分布式追踪。单个运行时请求已跨越四跳 —— edge → EPP（ext_proc）→ operator（CR patch）→ agent-runner → 模型 gateway —— 而目前关联它们意味着手工拼接每服务日志与审计行。

难点在结构上：唤醒路径是异步且最终一致的 —— EPP 修改 AgentTenant CR，operator 将其调谐为一个运行中的 pod；没有一个可挂子 span 的同步调用。一个真正的追踪方案需要在 edge 注入 W3C traceparent 传播，经 ext_proc 元数据携带进 EPP，再往下进入 runner 与 SDK 的一轮，并让 CR 携带一个关联 id，使 operator 的调谐能发出一个链接的 span，全部导出至一个 OpenTelemetry collector。这是一项前瞻工作，而非一次配置翻转。

7.5 日志

各服务通过一个共享的、基于 loguru 的 logger（get_app_logger）向 stdout 记录日志，供集群级聚合。由于是 loguru，消息使用花括号 {} 占位符 —— 一个 printf 风格的 %s 会被原样打印 —— 这是平台自己笔记里记下的一个小但真实的坑。结构化字段（account、session、run id）随日志记录一同传递，以便下游聚合据此透视；同样的标识符也作为 §7.3 中审计行的键。

7.7 公平性、唤醒踩踏与 warm pools

当前状态（诚实版）。每次唤醒都是一次冷启动（≈4 s）；没有 warm pool。由于空闲租户处于 0 副本，一次同步的突发 —— 早 9 点的登录浪潮，或一次定时作业扇出 —— 就是 N 个同时发生的冷启动，一齐冲击调度器、镜像缓存与节点容量。所设计的全局唤醒并发限制器（约 20 个在途）为踩踏封顶，但把它转化为一个队列；每账号并发上限（默认 3 会话）为单个吵闹的租户封顶。当前没有跨账号的集群级公平配额。

搭建一个 warm pool（提案）

三档，由廉到贵 —— 每档均可独立部署：

档位机制权衡
1 · 预热节点 / 预拉取镜像在一个专用节点池上保持 agent-runner 镜像已预拉取（一个极小的 image-holder DaemonSet 或节点镜像缓存策略）。从每次冷启动中移除镜像拉取延迟。最廉价，无需改应用；能省下数秒，但 pod 仍是从零创建。
2 · 预热的通用 pod 池维持 K 个从镜像启动但未绑定的备用 agent-runner pod（无 ACCOUNT_ID，仅一个临时 emptyDir）。唤醒时 operator 认领一个预热 pod 并把它绑定到账号，而非从冷态创建一个 Deployment。绑定是难点（见下）。成功时近乎即时。
3 · 预测式 / 定时预热在已知峰值之前预唤醒可能活跃的账号，由已采集的 183 天用量信号或一个排程驱动；定时作业（Phase 4）在一批作业触发前预热它将需要的 pod。既有的 persistent runner 类型即其手动版本。需要一个需求模型；若预测失误则浪费容量。
绑定约束（档位 2）

Kubernetes 无法把每账号的 subPath 卷热挂载到一个已在运行的 pod 上，因此一个被认领的预热 pod 有两种解法之一：(a) 应用作用域绑定 —— 预热 pod 挂载共享 RWX priva-export 根，运行时在认领时把作用域限定到 /<account_id>（最快，无需重启，但在 pod 被回收前隔离变为应用强制 —— 仅在配合 §4.5 出站控制与一条硬性的会话后回收策略时可接受）；或 (b) 预热后重建 —— 预热 pod 证明节点 + 镜像 + 进程就绪，随后一次快速的 Recreate 挂载真正的每账号卷（保留内核挂载边界，仍远快于冷态，因为节点与镜像都是热的）。规模测算：池 ≈ P95 峰值时预期的并发冷启动数；一个公平配额唤醒队列（跨账号轮询，而非 FIFO）可阻止一个账号的扇出饿死其他账号。

上游路径

kubernetes-sigs 的 Agent Sandbox 正为此提供一个 SandboxWarmPool CRD（warm pools + 挂起/恢复），并明确援引类 Claude-Code 的 agent（§9）。日后采用它，即把 Priva 定制的池换成一个标准的 —— 与保持运行时层可替换（§12）相一致。

7.8 故障模式与降级运行

当某个组件宕机时，还有什么仍能工作 —— SRE 首先索要的爆炸半径表。由架构推导而来；待在 Phase 6（§10）计划的混沌测试下验证。

宕机组件运行中的 pod新请求爆炸半径
agentgateway（edge）在途的流中断完全不可用 —— 无入口点全面。单一前门 → 运行 HA edge 副本。
control-panel / EPP已转向的请求完成无法转向新的 /api/sandbox/*；SPA + admin 也随之宕机（同一进程）对新流量全面。无状态 → N 副本本就是设计；单副本丢失可存活，EPP 全体丢失则为不可用。

单个租户 pod仅该租户该租户等待重启设计上隔离 —— 每租户一 pod 的意义所在。
模型 gateway（用户 BYOK）该用户的轮次失败—按用户隔离（BYOK）；非平台级事件。
HA 从何处最先见效

两个全面不可用的组件（edge、EPP）与那一个真正的 SPOF（data-spine）是排序后的 HA 投资重点；其余不是降级但仍服务，就是设计上隔离。此矩阵为推导得出，尚未验证 —— 组件击杀与 offboard→purge 混沌测试是一项 Phase 6 交付物。

8.1 环境

Dev（minikube）：./deploy/minikube/build.sh 构建/加载 5 个镜像（priva/{data-spine,control-panel,operator,agent-runner,nfs-xfs}:dev，Python 3.12-slim，uv；agent-runner 烘焙原生 claude CLI）；up.sh 运行一次幂等的 9 步拉起（打上 allowVolumeExpansion 补丁的 CSI hostpath → 命名空间 → dev NFS+quota → Gateway API v1.5 + GIE v1.5 CRD → 经 Helm OCI 的 agentgateway 1.3.0 → CRD/RBAC → 共享 secret → 控制平面 → edge）。经 port-forward svc/priva-gateway 8080:80 访问。

Prod（Helm + values-prod overlay）：该 chart 与原始 manifest 一一对应；values-prod.yaml 换用带固定标签的真实 registry、禁用 dev 存储、设置 storageBackend=cephfs（外部 CephFS/NFS CSI —— 无特权存储 pod）、一个持久的 5 Gi data-spine PVC、显式的控制平面 requests/limits，以及可固定的 JWT/HMAC secret。Gateway API、GIE 与 agentgateway 是前置条件，不在 chart 内。

8.2 变更工作流

前端热加载

SPA 在宿主上构建，并由 control-panel 经 StaticFiles 从磁盘提供，因此前端变更无需重建镜像：把新鲜的 dist/ 用 tar | kubectl exec 送进运行中的 pod，它即刻实时提供。热加载的文件在重新调度时丢失；使其持久化的是镜像重建。后端变更总是需要重建镜像。

8.3 可观测性（ADR 0002）

原始 prometheus-client，无框架。HTTP 计数/延迟记录于既有的 AccessLogMiddleware 内（标签：路由模板 handler、method、status；user_name 被刻意地从不作为标签 —— 基数无界）。领域计数器：agent_runs_started_total、agent_runs_finished_total{outcome}。多进程目录由启动器拥有（每次启动清空 + 重建，使陈旧的每进程文件无法永久虚增计数器）。/metrics 被刻意设为无鉴权（由网络控制；可选的将来 METRICS_TOKEN）。

8.4 迁移状态（strangler）

Phase 0–3 已完成，于 2026-06-21 合入，在 minikube 上端到端验证。遗留的 monolith（priva/）仍作为行为参照启动，将在 Phase 4 移除。完整的阶段计划见 §10。

8.5 数据生命周期、保留与 DR

用户数据存于何处、存多久、如何可证明地消失，以及如何在故障中存活。设计已具备接入点（CRD 的 desiredState、history-retention 开关），但尚无完整的生命周期或任何备份方案。

用户数据存于何处

数据位置
工作区 + 会话RWX priva-export 卷的每账号 subPath；~/.claude/projects 的 JSONL 就是会话的权威记录，外加 venv。
审计每账号 /audit/<account_id> 卷（按天分区的 JSONL）。
控制元数据data-spine —— account、quota、specs、registrations。永不含 transcript 内容。
凭证BYOK 存于 pod 自己的 /workspace/.claude/settings.json；用户 API 密钥在 data-spine 中经 Fernet 加密。

生命周期与被遗忘权

CRD 已建模若干状态：active → offboarding（pod 缩至 0，数据保留，访问撤销）→ purge（数据销毁）。建议新增、均未构建：一个可配置的保留窗口（purge 前的宽限）、法律保留（对指定账号阻断 purge），以及 purge 前的导出我的数据（一份工作区 + 审计打包）。

擦除与备份是同一个问题

一个站得住脚的被遗忘权，必须销毁每一份副本 —— 工作区 subPath、审计卷、data-spine 行、API 密钥密文，以及任何备份/快照 —— 随后发出一条防篡改的 purge 记录（唯一保留的产物）。没有一份「持有副本的每个备份」的清单，你就无法证明擦除，这正是二者不可分割的原因。

备份与 DR（当前缺失 —— 建议）

  • data-spine：单个 SQLite 文件 → 定时在线备份（WAL 拷贝）至节点外存储，并有文档化的 RPO（例如 ≤ 24 h）/ RTO；Postgres HA 路径（当前为 stub）才是真正的解法。
  • 工作区：在 prod CephFS/NFS 后端上按排程做每账号 CSI VolumeSnapshot。会话 JSONL 即记录，当前无任何其他冗余 —— 卷丢失即 agent 记忆丢失。
  • 恢复演练：未经测试的备份不算备份 —— 定期演练恢复，与 offboard→purge 混沌测试（Phase 6）一并进行。
诚实状态

CRD 生命周期状态已存在；保留窗口、法律保留、导出、擦除证明以及整个备份/DR 层都是建议，而非代码。在任何 HA 或合规主张之前先设定 RPO/RTO 目标。在 §12 中跟踪。

8.6 升级与发布生命周期

当 agent-runner 镜像、烘焙进去的 claude CLI 或 SDK 发生变化时，集群如何向前推进 —— 这是「SDK 变动」风险（§12）在运维上的对应物。

  • 控制平面：无状态服务正常滚动。两处要点：control-panel 在 :9000 上绑定进程内 EPP，因此按副本数扩缩/滚动，绝不用 uvicorn --workers；并且其每 pod 本地审计必须在运行 >1 副本之前迁入 data-spine（§7.3），否则一次滚动升级会分叉审计历史。
  • 租户 pod：CRD 携带每租户 image，因此集群可保持刻意的版本偏斜 —— 但当前没有任何东西治理发布。建议：一个金丝雀队列（少数账号钉在新镜像上），以一次 eval 通过为闸门，随后分阶段推进默认镜像。驻留的 pod 在其下次唤醒时取用新镜像 —— scale-to-zero 兼作对空闲用户的免费滚动升级，零协调停机。运行中的 pod 在会话结束时或管理员强制重启时排空并重建。
  • 会话兼容性：会话自愈（恢复时修复孤儿 tool-use）吸收轻微漂移；一次破坏性的 claude/SDK 变更需要一次会话格式兼容性检查，最坏情况下需为旧 transcript 提供一个只读回退（与推迟的 state-reader 相关，§5）。按镜像固定 CLI 版本，使偏斜显式化。
  • 回滚：由于唤醒会拉取当前默认镜像，回滚 = 把默认指回并强制重启；驻留的 pod 在下次唤醒时自愈。
Scale-to-zero 让升级变廉价

大多数 pod 处于关闭状态，因此多数用户在下次登录时升级，零协调停机 —— 这是租户模型一个被低估的好处。真正的工作是金丝雀/eval 闸门与会话格式兼容性检查，而非机制本身。

§9竞争格局与自建 vs 采用

对照厂商文档、许可证与新闻，截至 2026 年 7 月核实。对比以 Manus 一类的自主 agent 品类为中心 —— 给一个目标，agent 在自己的 sandbox 中端到端规划并执行，返回交付物 —— 同时纳入开源个人 agent、Anthropic 的第一方选项，以及 Priva 所组合的 K8s 基座。每一个都在至少一条决定性维度上未能满足 Priva 的需求集 —— 完整 Claude-SDK 面 × 每用户隔离 × 完全本地部署 × BYOK。

9.1 四个品类

Manus · Genspark · Devin · Flowith。重定向所指向的品类：托管产品，投入一个目标、产出一个成品，在厂商云中自主执行。业界一流的自主性 —— 而且，除一个部分例外，无法在你自己的网络上运行。

品类结论

打磨得当的自主性、零运维 —— 而对本地部署强制要求而言，皆不可选：仅 SaaS 且无 BYOK，Devin 的单租户 VPC 是唯一的部分例外（仍是厂商运营、仅限编码）。Manus 被 NDRC 拆分的 Meta 交易是一个活生生的提醒：即便是领导者，也背负着你从外部无法对冲的厂商延续性与地缘政治风险。

OpenClaw · Hermes Agent · OpenManus · OpenHands。可自托管且 BYOK —— 与 Priva 共享的信念 —— 但都构建为单用户守护进程或框架，无一是 Claude-SDK 原生，也无一具备 K8s 多租户运行时或集中治理。

品类结论

全部本地部署且 BYOK —— 而且全都是单用户守护进程或 DIY 框架。无人交付一个 K8s 原生、scale-to-zero、每用户一 pod、带集中治理、并以 Claude Agent SDK 为原生面的运行时。OpenClaw 的暴露实例记录，活生生展示了「数百名半可信内部用户」会对一个宿主特权的单用户设计造成什么 —— 正是 Priva 的每用户 pod 边界存在以防范的失败模式。

Claude Code on the web · Claude Managed Agents · Claude Team/Enterprise。「为何不直接买 Anthropic 的托管版」这一问题 —— 按定义具备完美的 Claude 兼容性，且有一个共同的答案：主权与 BYOK。

采用侧最尖锐的威胁

Managed Agents 是 Anthropic 明确地把 Priva 所构建的那一层产品化 —— sandbox、状态、秘密、编排，以 $0.08/用户小时计价，变动由版本化的 agent 配置吸收。因此自建论据必须立足于主权、BYOK 与产品面 —— 而非成本，在成本上租用者胜出。

E2B / Firecracker · agentgateway · Gateway API Inference Extension · kagent · Agent Sandbox（kubernetes-sigs）。它们不是竞争者 —— 而是 Priva 所组合（或可采用）的基座，也是其架构正成为新兴标准的最有力证据。

  • E2B Firecracker microVM 是 Manus 的 sandbox所运行于的东西 —— 位于 Priva 共享内核 pod 之上的硬件级隔离层。Priva 无需第二套编排器，只要把 runtimeClassName 翻转为 gVisor/Kata 即可达到同一层；边界是一次配置变更，而非重新设计。
  • agentgateway（Linux Foundation，v1.0.0，CNCF Agentic-AI 雷达 "Trial"）如今已由 kgateway 与 Istio 双双在 beta 中实现 —— Priva 的 edge 是一个主流路线的押注，而非异类。
  • Gateway API Inference Extension 达到 v1.0.0 并有合规实现；Priva 的 InferencePool + EPP 接线坐落于一个已稳定的上游 API 之上。
  • kagent（CNCF Sandbox）将 agent 定义为 CRD，但面向平台/DevOps 自动化，而非多租户个人助手。
  • Agent Sandbox（kubernetes-sigs，2026-03 公布）—— 为带挂起/恢复、warm pools 与 gVisor/Kata 运行时的单例有状态 agent 工作负载提供 Sandbox / SandboxWarmPool / SandboxClaim CRD，并明确援引「像 Claude Code 那样的 agent」。仍处于预发布 —— 但它恰是 Priva 每用户 scale-to-zero pod 的上游标准化，也是运行时层的一个候选未来基座。
战略解读

底层管道正在向 Priva 的形态收敛。它们无一交付控制台、会话持久化或 Claude SDK 功能映射 —— 即便 pod 运行时层被商品化，产品层仍保持差异化。把那一层设计得可替换（§12）。

9.3 自建 vs 采用：论据及其诚实的代价

为何自建

1 · 交集为空。完整 Claude-SDK 面 × 每用户隔离 × 本地部署 × BYOK，在任何品类中被零个产品满足 —— 商业 agent 缺主权/BYOK，开源 agent 缺多租户/SDK 原生性。
2 · 主权使商业一列出局。Manus、Genspark 与 Flowith 仅 SaaS 且无驻留控制；Devin 的单租户 VPC 是唯一的部分例外，仍是厂商运营且仅限编码。Manus 被 NDRC 拆分的 Meta 交易表明，即便领导者也背负厂商延续性风险。
3 · BYOK 在商业侧无处存在。Manus credits、Genspark credits、Devin ACU 都通过厂商计量。OpenClaw 的 OAuth 封禁证明自带订阅的取巧终会被切断；只有干净的 API 密钥 BYOK 模型才可持久。
4 · 每用户隔离是开源侧的缺口。OpenClaw 与 Hermes 是单用户宿主守护进程 —— OpenClaw 的暴露实例记录正是那种架构在规模下的表现。无人交付带治理的 K8s 每用户 pod scale-to-zero。
5 · SDK 原生性带来复利。这十者无一把 sessions、fork/rewind、hooks、subagents、权限模式作为一等公民暴露；每个 OSS agent 都重建了自己的 harness。Priva 继承 Anthropic 的升级路径。

它的代价（诚实版）

1 · 自主性的打磨是实打实的工作。Manus 与 Genspark 交付一个调校过的目标→交付物循环（规划、浏览器控制、产物生成、并行 VM 集群），零运维。Priva 的原始 SDK 会话 + 聊天/PTY/文件控制台并不自动等于那个产品；达到「给一个目标、拿回幻灯片」的对等仍是持续的 agent-UX 工程。
2 · sandbox 加固转移到你身上。Manus 把隔离外包给 E2B Firecracker 的专业团队；Priva 必须自己加固 pod 逃逸、出站与秘密 —— 而未决的 Web 终端发现（§4.4）正好印证了这一点。

§11设计演进与扩展路径

当前架构是为「一个用户从浏览器驱动一个 agent」而建。下述能力将其延伸至 agent 驱动 agent、人类带外审批，以及 agent 跨用户共享。对每一项，设计都已提供大部分基座；价值在于精准看清它在何处成立、又必须在何处改变。这些是设计方向，而非已承诺的路线图（§10）。

贯穿主线

每租户一 pod + EPP 转向 + 权限/hook 治理，事实证明是全部四项扩展的强力基座：一个已发布的 agent 不过是一个租户，一次 A2A 调用不过是一次唤醒，一次带外审批不过是一个持久化的 permission_request，而经纪的 MCP 鉴权，不过是 control-panel 为工具做它早已为 runner token 所做的事。而它们各自要求的回报，大多是已在 Phase 6 清单上的加固（NetworkPolicy、mTLS/JWKS、KMS/DEK），外加权限协调器的持久性。这些扩展并不与架构相抗 —— 它们兑现的是架构那些被推迟的安全支票。

11.1 Agent 间（A2A）互通

当前基座。agent-runner 已经经 MCP 消费工具（agent→工具）并运行 pod 内 subagents；agentgateway edge 是一个 AI 原生的 L7 代理；且 EPP 已提供每 agent 身份、按需唤醒与逐请求转向。多 agent 工作流巡视器已对多 agent 运行进行建模与持久化。

已有原型 —— priva-agent-gateway skill。A2A 在此并非假设：一个捆绑的 skill（services/agent-runner/.../bundled/skills/priva-agent-gateway）已让一个 Priva agent 经标准运行时 SSE 契约把任务委派给另一个。该机制刻意做得很薄 —— 这正是要点所在：一个 agent 调用另一个 agent，不过是一个 agent 充当运行时 API 的普通客户端，没有发明任何新协议。

它今天如何工作

调用方 agent 带 Authorization: Bearer <token> 将普通的 AgentRunRequest 主体 {message, session_id?} POST 至 POST /api/agent/run/stream（端点由 AGENT_SANDBOX_GATEWAY_URL 设定），流式接收 SSE 事件，丢弃中间的 assistant / tool_use / tool_result / task_* 事件，只保留终结的 result —— 其载荷已携带 session_id、is_error、num_turns、duration_ms、total_cost_usd 与 usage。多轮连续性是一个持久化在本地 session.json 中的、平台铸造的 session_id（不可变会话 id 原则，§2）。并发由一个对 <session_id>.lock 的非阻塞 fcntl.flock 守护，它快速失败（退出码 4）—— 因为远端 agent 保有磁盘上的对话状态，并发调用会将其破坏。bearer token 仅存于请求头中，从不抵达模型。

原型证明了什么它仍缺什么（一般化）
A2A 复用既有的 SSE + Bearer + 不可变会话契约 —— 无新协议，无新传输。鉴权是工作目录文件中的一个静态 bearer token，没有调用方身份 → 经纪的、按调用方限定作用域的 token（§11.4）与身份联邦（§11.5）。
跨 agent 成本归因已可处理：每个 result 都返回 total_cost_usd / usage，因此被调方可把花费上报给调用方。无发现/注册 —— 对端只是单个环境变量 → 一个 agent-card 注册表（§11.3）。
每会话串行化（flock）是 A2A 顺序保障的具体形态 —— 远端状态是权威的，不可被并发竞争。该锁守护的是一个会话的并发，而非跨 agent 的 A→B→A 递归 → 跳深 + 环路限制。
HITL 存在于委派接缝处：该 skill 指示调用方在执行破坏性生产操作前先与人类确认。该确认是提示指示的，而非平台强制的 → 审批收件箱（§11.2）；且被调方没有入站授权（谁可驱动它）→ 下方 §11.1 保障。

完整 A2A 带来什么。每个租户 agent 既成为其他平台 agent（例如新兴的 Agent2Agent 协议与 agent card）的调用方，也成为其可调用端点。一个外部 agent 寻址「用户 X 的 agent」；EPP 唤醒那个 pod 的方式与处理一次浏览器请求完全相同 —— 按需唤醒 + runner-token 模型几乎原封不动地映射到 A2A，而 gateway skill 就是调用方一半的可用证明。

未来用法。从原型到平台能力的路径清晰可辨：把 AgentRunRequest/SSE 契约提升为 Priva 原生的 A2A 方言，并加一个适配器，将外部 Agent2Agent / agent-card 映射到同一端点，从而让 edge + EPP 把每一个租户 agent 呈现为一个可寻址、按需唤醒的 A2A 对端，并以 runner token 为其能力凭证。这将解锁一张 agent 网格 —— 多跳 A→B→C 委派，而这正是多 agent 工作流巡视器已在 pod 内建模的 —— 其中已发布的「生产 agent」是它们各自的租户（§11.3），经这同一个 gateway、在经纪的按调用方凭证（§11.4）、强制的人类审批（§11.2）之下被抵达，成本则由每一跳已经返回的 total_cost_usd 跨网格汇总（§11.5）。

这要求的保障

一次入站 A2A 调用，是一个不受信的外部方在驱动一个特权 pod —— 经典的混淆代理问题。它需要：agent 级 ACL（谁可调用谁）、一个受约束的入站权限画像（绝不 bypassPermissions、一份扩展的禁用工具集、强制 hooks）、环路/递归限制（A→B→A）、限流，以及对每次跨 agent 调用的完整审计。BYOK 成本归因也会失效 —— 当 B 驱动 A 时由谁的密钥买单？（见 §11.5）。

11.2 异步 HITL 与 Feishu 审批收件箱

当前基座。同步的、会话内的 human-in-the-loop 已可工作：权限协调器发出一个 permission_request，挂起一个 pod 内的 asyncio.Future，并在 POST …/permission/respond 时解决它。推迟的 channel-connector（Phase 4）加上 channel_binding 表（Feishu 用户 ↔ account，已在 schema 中）提供了寻址。

收件箱带来什么。当一个 agent 在脱离运行时命中一个审批点 —— 一个定时作业、一个 A2A 驱动的任务、一个长批处理 —— 而没有浏览器打开时，把请求路由到用户的 Feishu 收件箱；人类在那里审批；agent 随后恢复。

架构上的难点

pod 内的 asyncio.Future 是易逝的。若 pod 在等待一个耗时数小时的人类期间缩至零，待决的决策就丢失了。因此异步 HITL 迫使当前 scale-to-zero + 内存协调器的设计获得持久性：(1) 持久化待决审批（data-spine 或 PVC），而非一个 Future；(2) 让有未决审批的 pod 豁免于空闲回收，或使该决策在唤醒时可重新水化；(3) 用短有效期签名审批链接，使一条 Feishu 消息无法被伪造成一次审批；(4) 一条默认为拒绝的超时/升级策略；(5) 对审批者身份的审计。权限模型是正确的接缝 —— 改变的是持久性与投递，而这恰是 Phase 4 的调度器 + channel-connector 工作。

11.3 可共享 / 可发布 agent 与文件系统保障

当前基座。一个 subagent + 其 skills + MCP 服务器 + system prompt + hooks 已构成一个可复用的「agent 定义」，而 Skills hub 是一个可用的发布/消费模式。由此衍生两种共享模型，风险迥异：

  • (a) 发布配置 —— 他人在他们自己隔离的 pod 中实例化该 agent。安全，且契合当前设计：隔离与 BYOK 保持在每个实例化者一侧。
  • (b) 共享一个运行中的 agent —— 他人向你的实例发送任务。危险：他们的输入现在驱动着一个位于持有你工作区、你的 BYOK、你的 MCP 凭证的 pod 内的 agent。
干净的模型

把一个已发布的 agent 当作它自己的租户 —— 它自己的 AgentTenant CR、它自己的 pod、它自己作用域受限的卷与服务凭证 —— 由他人经 A2A（§11.1）在按调用方鉴权与审计之下调用。这原封不动地复用了 scale-to-zero、pod 隔离与 EPP 转向：一个可发布 agent 不过是一个「用户」为共享服务身份的租户。

文件系统保障（模型 b，或任何入站共享的会话）

一个不受信的消费方可能要求一个共享 agent 读取作者的文件并返回 —— 混淆代理式的数据外泄。必备防护：一个仅注入 agent 所需内容的受囚禁 / 易逝暂存工作区，绝不含作者的 ~/.claude/projects；只读或每次调用的临时目录；一个锁定的权限画像 + 强制 hooks；一条默认拒绝的出站 NetworkPolicy，使其既不能提权工具也不能外泄；以及凭证解耦 —— 专用服务凭证或经纪的 MCP token（§11.4），绝不用作者的个人 BYOK。共享放大了爆炸半径，这把 §4.4 的 Web 终端 / NetworkPolicy 加固从「推迟」提升为「前置条件」。

11.4 统一 MCP / skill 鉴权

当前基座。MCP 配置来自 .mcp.json + settings.json；内置的 priva_File 服务器在进程内且无需鉴权。然而外部 MCP 服务器的凭证当前是每 pod 存放的（settings / secret 挂载）—— 实质上是每用户手动配置。

统一带来什么。当众多用户的 agent 抵达同一批内部 MCP 服务器（工单系统、数据库、内部 API）时，任何用户都不应持有原始服务凭证。沿新兴的 MCP OAuth 2.1 / resource-indicator 方向，一个中心经纪方签发每用户、每服务作用域受限的 token，把用户身份贯穿传递，使 MCP 服务器强制每用户访问，并集中轮换与吊销。

设计契合度

control-panel 是天然的经纪方 —— 它已在铸造 runner token 并掌握身份。它会为每个 MCP 服务器登记其鉴权方式（OAuth client / API key / mTLS），在唤醒时或按需经纪短生命周期的每用户访问 token，作用域受限地注入 pod 的 MCP 配置，以实际用户身份审计 MCP 工具调用，并在不触碰 pod 的情况下轮换。会向外部服务 shell out 的 skills，也以同样的经纪方式获得凭证，而非嵌入秘密。

需管理的张力

这会把高价值秘密集中到控制平面 —— 与「控制平面绝不接触运行时数据」原则相冲突。化解之道是让经纪方只持有长生命周期的刷新材料，并交给 pod 短生命周期、作用域受限的访问 token，这反而强化了 Phase 6 的每账号 KMS/DEK 需求，而非与之相悖。

11.5 横切影响

上述四项扩展浮现出同一小撮平台级问题 —— 那些值得一次性、集中决定，而非逐特性决定的问题：

关注点它迫使什么
BYOK 下的成本归因A2A 与共享 agent 打破了「用户自己的密钥买单」。需要每次调用的归因，并很可能是一种混合：服务 agent 携带一个服务密钥，用量回收计费。这与无计量代理非目标存在真实张力 —— 可作为仅面向共享/服务 agent 的、可选启用的计量面来化解，个人 BYOK 不受触动。
身份联邦当前为 JWT/HS256 + API 密钥。A2A 与企业级 HITL 需要联邦身份（OIDC/JWKS），使外部平台与 Feishu 身份映射到 Priva 账号。channel_binding 是一个开端；Phase 6 的 mTLS/JWKS 工作是通用层。
入站信任与提示注入每一次入站 A2A / HITL / 共享驱动，都是进入特权 pod 的不受信输入 —— OpenClaw 的教训（§9）。一个加固的「入站画像」（受约束工具、强制 hooks、出站 DLP）成为一等构件，而非逐 agent 的事后补救。
版本化与注册表治理一个已发布的 agent 是一个共享依赖：消费方需要固定版本与安全发布；一个已发布 agent 注册表需要管理员审查、溯源与签名（供应链姿态）—— 与 Anthropic Managed Agents 的版本化配置及 Skills hub 相呼应。
agent 网格 / 跨 pod 编排pod 内 subagents 自然延伸为一个主管派生易逝的 worker pod（各为其自己的 AgentTenant CR）。工作流巡视器 + EPP + A2A 已然是其基座。

  • 如果我 pod 的卷坏了，我的会话历史与工作区就这么没了吗？什么被备份了？（§8.5 —— 当前无备份；JSONL 是唯一副本。）
  • 付费的是我的 API 密钥 —— 有什么能阻止一个失控的 agent 在我离开时一夜烧光它？（§12 —— 无花费上限或熔断。）
  • 究竟谁能读到我的文件与 transcript —— 管理员？其他用户？（控制平面从不看到运行时数据，§2 —— 但管理员跨文件浏览，§5，以及 Web 终端暴露，§4.4，使这个干净的答案复杂化。）
  • 说实话，为什么不直接用 claude.ai 或 Claude Code on the web？（§9 —— 主权 + BYOK 就是答案，但控制台必须跟上节奏。）

14.2 工程负责人 —— 「为何自建，又凭什么它不会被丢弃？」

  • Anthropic 以 $0.08/会话小时租用的正是这套运行时，且 sandbox、vaults 与 SDK 变动都替你搞定。请为改而自建并运营的人力编制作出论证。（§9.3 —— 论据立足于主权/BYOK/产品，绝不立足于成本。）
  • 你被焊死在一个快速演进的 SDK/CLI 上。当某一周一次破坏性变更搁浅了在线会话，会发生什么？（§8.6 升级生命周期，§12 变动。）
  • 这是 Manus 一类的自主性，还是一个聊天 + 终端的外壳？给我看「给一个目标、拿到一份成品交付物」的路径。（§9 诚实代价卡片，第 1 条 —— 真实的、持续的 agent-UX 工作。）
  • Agent Sandbox 可能在 12–18 个月内商品化 pod 运行时层。为什么这里没有一半被浪费？（§9 / §12 —— 保持运行时层可替换，在租户/控制台/BYOK 的上层做差异化。）
  • 你声称「数百」。到 2000 时什么会崩，多集群 / HA 的方案又在哪里？（kopf 逃生舱 >800 CR；单命名空间 alpha；data-spine SPOF，§7.8。）

14.3 安全负责人（CISO）—— 「我的爆炸半径是多大？」

  • 一个拿到 shell 的租户能读取共享签名密钥，并为任意账号或管理员伪造一枚 token —— 而你却未修复就发布了它。为什么其他任何事情反而被优先讨论？（§4.4 —— 未决，阻断上线。）
  • BYOK 指向任意 base URL，加上未受治理的出站，意味着 agent 能把我们的数据寄到任何地方。「主权」何以成立？（§4.5 —— 最尖锐的缺口；出站控制未构建。）
  • Skills 与 MCP 服务器是特权 pod 中未经审查的代码。有什么能阻止一个被投毒的共享 skill？（§12 供应链；§11.3 —— 尚无签名/审查/溯源。）
  • 为持有 PTY、运行任意代码的半可信用户提供共享内核隔离 —— gVisor/Kata、NetworkPolicy、mTLS 在哪里？（§4.3 —— 全在 Phase 6。）
  • 来自被抓取页面或文件的提示注入 → 外泄。实际的防御是什么，而非愿景？（§11.5 入站信任画像；OpenClaw 的教训，§9。）
  • 你宣称「集中强制的护栏」，但管理员→runner 的配置通道在 K8s 中悄然断开 —— monolith 写入 control-panel 自己本地的 .priva.settings.yml，而 runner 读取的是每账号的另一份副本，因此 enforced_hook_ids 从来没有写入方，强制 hook 从未抵达任何一个 pod。还有什么是「宣称却未接线」的？（hooks 已修复：钩子策略现经 data-spine hook_policy → 会话构建时的 runner 快照下发，且位于账号挂载之外，抗篡改。该通道上的其它旧开关 —— preset-prompt、risky-tools、敏感模式/PII、cli-path、history-retention —— 仍走旧路，是下一步迁移，§5 配置开关。）

14.4 SRE / 运维 —— 「凌晨 3 点会发生什么？」

  • data-spine 是一个无备份的 SQLite 写者 —— 一个没有 runbook 的告警。RPO/RTO？恢复演练？（§7.8 故障矩阵；§8.5 —— 未构建。）
  • 跨四跳异步唤醒路径没有端到端追踪。我如何对一个缓慢或失败的请求做根因分析？（§7.4 —— 未实现；异步 CR 唤醒是难点段。）
  • 早 9 点是 N 个同时的冷启动。容量模型是什么，warm pool 又在哪里？（§7.7 —— 三档设计已提案，均未构建。）
  • control-panel 审计是每 pod 本地的，因此我无法在不分叉历史的情况下以 HA 运行它。修复日期？（§7.3 / §8.6。）
  • 向数百个驻留 pod 安全地滚动一个新 runner 镜像 —— 并安全回滚。给我看流程。（§8.6 —— 金丝雀 + eval 闸门；scale-to-zero 有帮助，治理才是工作量。）

14.5 合规与财务 —— 「我们能向审计师与预算为此辩护吗？」

  • GDPR 擦除：证明一名离职员工的数据 —— 包括每一份备份 —— 都已消失。（§8.5 —— 擦除与备份是同一个、未构建的问题。）
  • 数据在物理上存于何处，保留窗口是多久，是否有法律保留？（§8.5 —— 建议，未构建。）
  • 你的竞争者声称 SOC 2。我们的控制框架与审计证据方案是什么？（审计轨迹已有，§7.3；正式的合规姿态尚未成节 —— 一个未决缺口。）
  • BYOK 意味着无中心计量 —— 我们如何在数百名用户间预测、归因并封顶花费？（§7.6 pod 自行上报；§11.5 归因；§12 封顶 —— 均未构建。）
  • 相对于就为同样的人力直接购买 Claude Enterprise 席位的总体拥有成本？（§9.3。）
诚实的记分卡

把上述每一项质询，按团队今天实际能公开说出口的程度分类：

  • 现在可答 —— 租户隔离模型、主权/BYOK 论据、自建 vs 采用逻辑，以及已交付的功能面（§3–§6、§9）。这些能挺过会议室。
  • 已设计，未构建 —— warm pools、备份/DR、追踪、统一鉴权、HITL 收件箱（§7.7、§8.5、§7.4、§11.4、§11.2）。纸面上有可信的答案；无一经过实战。
  • 未决且阻断 —— Web 终端秘密暴露（§4.4）与出站/BYOK 外泄（§4.5）。在它们闭合之前，给 CISO 的诚实答案是「尚未」，而这正是决定上线与否的答案。

本节设定的检验很简单：团队能否毫不退缩地给出这些答案？在不能之处，本规格至少完成了它唯一不可让步的职责 —— 在评审者之前先把缺口说出来。
